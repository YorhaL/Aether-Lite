# Aether Lite 定位与主版本差异处理策略

本文定义 Aether Lite 的长期产品边界，以及从 Aether 主版本同步代码时的处理规则。Lite 不是主版本迁移过程中的临时形态，也不是通过功能开关关闭部分能力的兼容发行版；它是面向团队内部 API 分发的独立精简版本。

数据库的具体演进规则见 [Aether Lite 数据库演进策略](lite-database-strategy.md)。

## 产品定位

Aether Lite 是自托管的内部 AI API 分发网关，重点保留以下能力：

- 用户、API Key、权限和基础管理能力。
- 自定义 Provider、Endpoint、凭据及模型路由。
- 客户端与上游格式一致时的请求和响应透传。
- 负载均衡、健康监控、用量记录和基础额度控制。
- PostgreSQL、SQLite，以及部署形态需要的运行时协调能力。

Lite 不面向公开商业运营，不承担套餐销售、充值支付、返利增长、第三方账号托管或跨协议 API 适配。设计优先级依次是边界清晰、运行稳定、易于审计和维护成本可控，而不是保持主版本的功能数量或源代码形状。

## 与主版本的功能边界

| 领域 | 主版本能力 | Lite 策略 |
| --- | --- | --- |
| Tunnel 与代理网络 | Aether Tunnel、代理节点及相关网关代理管理 | 删除。网关仅保留向已配置上游发送 API 请求所必需的转发能力，不保留 Tunnel、代理节点编排或对应管理面 |
| Provider | 多种内置 Provider、OAuth、账号导入和号池管理 | 只保留自定义 Provider；凭据由管理员直接配置，不做 Provider OAuth，不保留号池 |
| API 格式 | 跨供应商请求/响应格式转换和适配 | 只做同格式透传；客户端请求格式必须与目标 Endpoint 的上游格式一致，不做转换、补偿或降级适配 |
| 钱包与额度 | 套餐、充值、支付、退款、兑换等商业流程 | 钱包只表示内部额度，保留额度查询、分配、调整和用量扣减所需的基础能力 |
| 增长与支付模块 | 邀请返利、支付配置及相关运营能力 | 删除 |
| 通知模块 | Server 酱、Bark 等外部推送渠道 | 删除 |
| 数据库 | PostgreSQL、SQLite、MySQL/MariaDB 及其迁移 | 只支持 PostgreSQL 和 SQLite；不保留 MySQL/MariaDB 驱动、迁移、配置或兼容逻辑 |
| 版本迁移 | 可能包含旧 Python/Alembic 升级和过渡路径 | 只支持从当前 Rust 主版本切换；不保留 Python 运行时、过渡模式、兼容层或 wrapper |

## “删除”所代表的语义

Lite 中被删除的功能应当视为从未存在，而不是“存在但不可用”。除保持当前 Rust 主版本数据库兼容所必需的历史 schema 外，代码和产品表面不得留下这些功能的痕迹：

- 不保留 feature flag、运行时判断、空实现、兼容 facade、wrapper 或仅用于返回错误的 handler。
- 不保留 API 路由、请求字段、响应字段、权限项、配置项、环境变量、后台任务或指标分支。
- 不保留前端页面、菜单、API client、状态管理、文案、图标或国际化条目。
- 不返回“功能已删除”“Lite 不支持”“尚未用 Rust 实现”或“无法转换格式”等说明。不存在的路由按普通未匹配路由处理。
- 不为方便以后同步主版本而建立与已删除领域同名的占位模块。

数据库是唯一需要区分“结构存在”和“能力存在”的地方。主版本已发布的 PostgreSQL/SQLite 核心 migration 必须保持版本号、顺序、内容和 checksum 一致，因此其中属于已删除功能的表或字段可以继续存在；Lite 业务代码不得读取、写入或重新暴露这些结构。

## 同步主版本的处理流程

从主版本合入变更时，先按实际行为分类，再处理代码冲突：

1. **Lite 保留领域的通用变更**：正常同步，包括缺陷修复、安全修复、性能改进和必要重构。
2. **完全属于已删除领域的变更**：整体忽略，不移植类型、路由、配置、测试或文档。
3. **同时影响保留和删除领域的跨领域变更**：只提取保留领域需要的行为，并消除对已删除领域的依赖；不得为了保持主版本调用链而引入空实现。
4. **API 格式相关变更**：同格式透传、安全校验和通用传输修复可以同步；请求/响应转换、协议映射和供应商特化适配不进入 Lite。
5. **数据库变更**：主版本新增的 PostgreSQL/SQLite 核心 migration 原样同步，即使它服务于 Lite 已删除的功能；MySQL/MariaDB migration 直接忽略。Lite 独有数据变更进入独立扩展迁移链。
6. **依赖与架构重构**：以 Lite 当前产品边界为准重建最短依赖关系，不以维持主版本模块层级或兼容 facade 为目标。

发生冲突时，正确结果不是“尽量让 Lite 与主版本代码相同”，而是同时满足两项约束：保留领域获得主版本的有效修复，已删除领域没有通过依赖、类型或占位代码重新进入 Lite。

## Lite 独有功能的演进

Lite 可以增加独有功能，但新增能力必须符合内部 API 分发定位：

- 不把 Lite 重新扩展为商业 SaaS、第三方账号托管平台或协议转换网关。
- 优先复用稳定的领域接口，不依赖核心 migration 中仅为兼容保留的废弃业务表。
- 需要持久化时，先判断该变更是否应进入两边共用的核心迁移；Lite 私有数据遵循独立迁移链和扩展表策略。
- 对外 API 默认延续同格式透传原则。任何跨格式适配需求都应先重新评估产品定位，而不是直接增加转换分支。
- 新模块使用当前领域名称，不采用 `legacy`、`compat`、`phase`、`bridge` 等过渡性命名。

## 变更验收清单

同步主版本或新增 Lite 功能时，至少确认：

- 变更是否属于 Lite 明确保留的产品领域？
- 是否重新引入了已删除功能的依赖、路由、配置、前端入口或提示文案？
- 是否引入了跨 API 格式转换或 Provider OAuth/号池逻辑？
- 钱包变更是否仍然只服务于内部额度，而非交易或营销流程？
- PostgreSQL/SQLite 核心 migration 是否与对应主版本逐字节一致？
- Lite 独有数据库变更是否进入独立迁移链？
- 是否没有引入 MySQL/MariaDB 或旧 Python/Alembic 运行时兼容？
- 后端、前端、部署文件和文档是否共同遵守同一边界？
- 是否执行了格式化、编译、相关测试和 schema 一致性检查？

## 文档优先级

当主版本文档、历史实现和 Lite 当前行为不一致时，按以下顺序判断：

1. 本文定义的 Lite 产品边界。
2. Lite 数据库演进策略。
3. Lite 当前公开 API 和已验证行为。
4. 主版本文档和实现，仅作为同步来源，不自动成为 Lite 的功能承诺。

任何需要突破前两项约束的变更，都应先修改策略文档并明确迁移影响，再进入实现。
